# Поведение React ↔ Go: нормативный контракт v0.2

Читать вместе с [OpenAPI](./openapi.yaml) и [SSE](./chat-events.md).
Это решения для MVP, обязательные для обеих реализаций. Спецификация не означает,
что эти функции уже реализованы. [Примеры](./examples/scenario.json) синтетические.

## 1. Общие правила запросов

- React обращается только к Go через /api/v1 на том же origin (dev proxy и production routing).
- Сессия HttpOnly cookie buddy_session, SameSite=Lax, Secure при HTTPS. Ответы с личными
  данными и demo/session: Cache-Control: no-store. На POST/PATCH/DELETE проверять Origin
  по allowlist; отсутствие/чужой Origin для браузерного API — 403 ORIGIN_FORBIDDEN.
  Интеграционные тесты задают правильный Origin явно. SameSite не заменяет проверку Origin.
- Demo accounts/session доступны только при DEMO_MODE; иначе 404. Test accounts синтетические.
  Выход гасит cookie и серверную сессию; повтор выхода возвращает 204, даже без сессии.
- Маршруты стажёра доступны роли intern. Наставник может читать me, выйти,
  получить список своих стажёров через GET /mentor/interns и план через
  GET /mentor/interns/{id}/plan. Назначение проверяется на сервере. Чужой
  стажёр возвращает 404. План доступен только для чтения, allowed_statuses
  пуст для каждого шага. До подключения очереди open_questions равен null.
  Маршруты другой роли возвращают 403 ROLE_FORBIDDEN.
- После 401 клиент отменяет запросы и очищает кеш; запоздалый ответ старой сессии
  не должен заново заполнить кеш нового пользователя.
- Неизвестные поля тела запроса отклонять с 422 VALIDATION_ERROR. Неизвестные поля
  ответа клиент может игнорировать. Пустое/пробельное сообщение недопустимо.
  Лимит 8000 — Unicode code points, а не байты и не длина UTF-16 JS-строки.
- Даты RFC 3339 UTC. ID непрозрачные, URL-параметры кодируются. GET ничего не создает.
- Существование чужого объекта скрывается ответом 404 NOT_FOUND. Роль и доступ
  проверяются для каждого запроса, документа и вызова инструмента, не только в UI.

## 2. Создание диалога и отправка

1. Фронт создает client_conversation_id UUID при намерении создать диалог и хранит его
   до получения результата. POST conversations принимает этот ID и optional step_id.
2. Сервер атомарно проверяет уникальность (user_id, client_conversation_id).
   Первый запрос — 201, повтор с теми же параметрами — 200 и тот же Conversation.
   Другие параметры — 409 IDEMPOTENCY_CONFLICT. Ключ не истекает раньше диалога.
3. Conversation.step_id неизменяем. Контекст читается из принадлежащего пользователю плана.
   title при создании — название шага или «Новый диалог», может позже обновляться сервером.
4. Фронт создает UUID client_message_id для новой отправки. Сервер проверяет в порядке:
   сессия/доступ → валидность → существующий ID → занятость генерации.
5. При совпавшем ID и тексте — 409 MESSAGE_ALREADY_EXISTS, при другом тексте —
   409 IDEMPOTENCY_CONFLICT. Исходный текст сравнивается без неявного trim/переписывания.
   UUID уникален внутри диалога и хранится весь срок жизни сообщения.
6. Если ID новый, но генерация занята — 409 GENERATION_IN_PROGRESS, без записи нового вопроса.
7. User (completed) и assistant (generating) сохраняются атомарно до message.started.
   assistant.in_reply_to_message_id указывает на user.id. Для user это поле null.
   Одна генерация на диалог обеспечивается сервером, в том числе при двух вкладках.

GET messages возвращает серверный порядок записи: user, его assistant, следующий user.
Сортировки только по created_at недостаточно. Частичный текст сохраняется не реже раза
в секунду, а финал — до terminal event. Черновик и request_ids сохраняются атомарно до
action.proposed. Финальное сообщение включает все созданные связи, даже при сбое LLM.

При потерянном POST-ответе клиент сначала ищет user по client_message_id в истории,
затем assistant по in_reply_to_message_id. Если записи нет, разрешен явный повтор
с тем же UUID. Для нового вопроса или осознанного повторения failed/interrupted — новый UUID.

## 3. Поток, таймаут и восстановление

User.status всегда completed. Assistant: generating → completed | failed | interrupted.
failed/interrupted содержат ApiError в message.error (код читается как message.error.error.code).
Другие состояния не содержат error. Отсутствие подходящих документов — нормальный completed
с честным ответом и пустыми sources, а не техническая ошибка.

До открытия потока Go возвращает HTTP JSON-ошибку. После 200 SSE — message.failed с
сохраненным Message. message.completed/message.failed последнее событие; затем EOF.
Если соединение закрыто, событие доставить нельзя: сервер сохраняет interrupted.
На лимите 120 с — failed/GENERATION_TIMEOUT. При рестарте Go зависшие generating
переводятся в interrupted. При завершении раньше обнаружения disconnect итог completed сохраняется.

Heartbeat каждые 15 с во время ожидания; proxy buffering отключен, таймаут прокси больше 120 с.
Go отменяет LLM/чтение инструментов при disconnect, но не уже подтвержденную отправку заявки.
Фронт при восстановлении опрашивает GET раз в 2 с. Через 130 с без конечного состояния
показывает ошибку восстановления и ручное обновление, не запускает генерацию заново.
Смена диалога отменяет текущий reader. Автоматического SSE replay в MVP нет.

ChatEvent в OpenAPI описывает разобранные {event,data}. По сети event и JSON data передаются
строками SSE. action.proposed требует request.status=draft; completed/failed требуют
соответствующего статуса Message. Эти межполевые условия проверяются дополнительно к схеме.

## 4. Заявка: версии, подтверждение, состояния

Только агент готовит черновик. Вызов инструмента создания внешней заявки возможен лишь
через подтвержденную сервером операцию; текст «подтверждаю» в чате не заменяет POST confirm.

- draft_version — версия параметров (resource, permission, reason), меняется при редактировании draft.
- revision — версия всей записи, начинается с 1 и растет на каждом изменении, включая status_checked_at.
  Фронт принимает только большую revision. Время updated_at не используется для разрешения гонок.
- Повторный запрос инструмента для того же пользователя/ресурса/права возвращает уже активную
  заявку (draft/submitting/pending), а не создает дубль. Если доступ уже выдан — сообщает доступность.
  После rejected/failed новый черновик допустим по явному новому запросу пользователя.
- Старые черновики не подтверждаются при наличии другой submitting/pending/granted заявки
  на тот же доступ: 409 REQUEST_CONFLICT. Сервер проверяет доступ заново.

Порядок confirm: права → блокировка записи → текущее состояние → версия → действие.

| Состояние до confirm | Поведение |
|---|---|
| draft | Проверить draft_version; атомарно перейти в submitting, отправить |
| failed | Проверить версию и доказанное отсутствие внешней заявки; повторить тем же request_id |
| submitting | Вернуть 202 и текущую запись; ничего не отправлять повторно |
| pending / granted / rejected | Вернуть 200 и текущую запись; ничего не отправлять повторно |

Для draft/failed неверная версия — 409 DRAFT_CHANGED; никаких побочных действий.
Для уже отправленных записей stale version не мешает вернуть прежний результат.
При 200 статус ответа pending/granted/rejected/failed; при 202 — submitting.
Достоверная ошибка внешней отправки сохраняется как failed и возвращается записью 200,
а не потерянной JSON-ошибкой. Ошибка до принятия операции может вернуть 503 ApiError.

Переходы: draft → submitting → pending → granted | rejected.
submitting → granted/rejected также допустим, если сервис ответил окончательным результатом сразу.
submitting → failed только при достоверном отсутствии внешней заявки; failed → submitting при повторе.
Неизвестный сетевой исход остается submitting до сверки; его нельзя объявлять failed только по таймауту.
granted/rejected — конечные состояния данной заявки. Редактировать можно только draft.

На внешнем вызове используется idempotency key=request_id или эквивалентная проверка
по client reference. Без поддержки такой сверки адаптер не должен автоматически повторять
неопределенную запись. Для нашей имитации поддержка обязательна.
Принятие confirm и задача отправки сохраняются до вызова сервиса; восстановление после
рестарта возобновляет отправку/сверку без дублей (например, через транзакционную очередь в БД).

external_id обязателен для pending/granted/rejected, null для draft/failed. submitting
может иметь номер при уточнении результата. failure_reason обязателен для failed/rejected.
status_checked_at — время последней успешной сверки, а не время последнего GET клиента.
GET возвращает сохраненное состояние. Go синхронизирует активные заявки с имитацией
не реже чем раз в 5 с; неуспешная проверка не обновляет status_checked_at.

## 5. План и действия пользователя

Для MVP шаги имеют одинаковый вес. progress_percent=floor(100*completed/total), пустой план — 0.
next_step_id — первый незавершенный неблокированный шаг в серверном порядке; null означает,
что доступного шага нет (все завершены или оставшиеся заблокированы). UI различает это по steps.
Зависимости шагов и необходимые права хранятся на сервере; фронт их не вычисляет.

allowed_statuses содержит разрешенные цели PATCH. blocked_reason обязателен как непустая
строка при blocked, иначе null. Повтор PATCH текущего пользовательского статуса возвращает 200
без изменений; попытка перехода вне allowed_statuses — 409 STEP_TRANSITION_FORBIDDEN.

В выбранном сценарии создание черновика сохраняет его связь со шагом; после принятия confirm
зависимый шаг blocked. Отказ/failed оставляют причину блокировки и путь решения через чат.
После granted шаг возвращается в in_progress, открывается возможность completed.
Сам факт выдачи доступа не означает выполненную настройку окружения.
Проверка ограничений повторяется сервером при PATCH, даже если UI показывал кнопку.
Изменение заявки и зависимого плана фиксируются согласованно; следующий GET plan видит результат.

### Подтверждения чекпоинтов (#42)

- `completion_policy` определяет нужные роли: `intern`, `mentor` или `both`.
  В `both` порядок свободный. С одной отметкой шаг `in_progress`, а `awaiting_role`
  указывает оставшуюся роль. При блокировке статус `blocked` имеет приоритет.
  Шаг с обеими отметками учитывается в прогрессе один раз. Оба GET плана и
  список наставника используют одну формулу и один порядок шагов.
- `confirmations` содержит активные отметки с ролью, ID автора и временем UTC.
  Отзыв собственной отметки возвращает шаг в работу и сохраняет отметку другой
  роли. Блокировка доступа или незавершённая зависимость запрещает новое
  подтверждение, но допускает отзыв своей отметки. Ранее завершённые зависимые
  шаги сохраняют отметки и завершённость. При снятии блокировки доступа статус
  восстанавливается с учётом сохранённых отметок.
- `template_key` стабилен в пределах плана. У старых шагов он равен ID,
  `period` равен null, `instructions` совпадает с `description`, а
  `resources` пуст. Новые шаги по умолчанию имеют политику `intern`.
  Для ресурса без известного URL передавайте `url: null` и при наличии пояснение
  в `note`. Период из каталога используется как текст.
- `PUT /onboarding/steps/{step_id}/confirmation` действует от имени стажёра,
  `PUT /mentor/interns/{id}/steps/{step_id}/confirmation` — от имени назначенного
  наставника. Оба принимают JSON `{confirmed, revision}` и возвращают Plan.
  `confirmed: true` устанавливает отметку, `false` отзывает её. Автор
  определяется сессией. Передавать ID автора или команды в теле нельзя.
- `allowed_actions` описывает действия текущей сессии с собственной отметкой:
  `confirm` или `revoke`. Несовместимая роль либо попытка изменить отметку
  другого автора возвращает 403 ROLE_FORBIDDEN. Чужой план, шаг или назначение
  возвращает 404 NOT_FOUND. Для JSON без обязательных полей, с лишними полями
  или некорректными значениями сервер возвращает 422 VALIDATION_ERROR.
- `revision` — версия снимка плана, одинаковая у всех его шагов. Изменения
  плана, отметок или сохранённого состояния доступа могут её увеличить.
  Повтор уже достигнутого результата своей операции возвращает актуальный план
  без изменения отметки, времени и версии, включая повтор со старой версией.
  Если результат ещё не достигнут, устаревшая версия даёт 409
  CHECKPOINT_REVISION_CONFLICT. Перечитайте план и сверяйте отметки перед
  новым действием. Актуальная версия при незавершённых зависимостях или
  отсутствии доступа даёт 409 STEP_TRANSITION_FORBIDDEN.
- Старые поля сохраняются. Для `intern` PATCH в `completed` ставит отметку
  стажёра, а переход из `completed` в рабочий статус снимает её. PATCH может
  менять рабочие статусы шага без отметок. При `mentor` и `both` поставить
  или снять отметку можно только через PUT, и PATCH не меняет статус шага с
  отметкой. GET для наставника по-прежнему возвращает пустой `allowed_statuses`.
- Примеры запросов, обеих последовательностей подтверждения и ошибок есть
  в [fixtures чекпоинтов](examples/checkpoints.json).

## 6. Стабильные ошибки

| HTTP | error.code | Действие фронта |
|---|---|---|
| 400 | BAD_REQUEST | Сообщить о неверном формате запроса |
| 401 | UNAUTHENTICATED | Очистить сессию UI, открыть вход |
| 403 | ORIGIN_FORBIDDEN / ROLE_FORBIDDEN / OPERATION_FORBIDDEN | Показать запрет, не повторять автоматически |
| 404 | NOT_FOUND | Объект отсутствует или недоступен |
| 409 | IDEMPOTENCY_CONFLICT | Не повторять с измененными параметрами под прежним ID |
| 409 | MESSAGE_ALREADY_EXISTS | Прочитать историю и найти исходный UUID |
| 409 | GENERATION_IN_PROGRESS | Прочитать историю, дождаться завершения |
| 409 | DRAFT_CHANGED | Обновить карточку и запросить новое нажатие |
| 409 | REQUEST_CONFLICT | Обновить список заявок; не отправлять дубль |
| 409 | STEP_TRANSITION_FORBIDDEN | Обновить план и объяснить причину |
| 409 | CHECKPOINT_REVISION_CONFLICT | Перечитать план и сверить отметки перед повтором |
| 409 | INTERN_ALREADY_ASSIGNED | Обновить списки свободных и назначенных стажёров; чужое назначение не менять |
| 422 | VALIDATION_ERROR | field_errors с именами полей; показать у формы |
| 429 | RATE_LIMITED | Показать ожидание; учитывать Retry-After, если передан |
| 500 | INTERNAL_ERROR | Сообщить trace_id, не раскрывать внутренние детали |
| 503 | SERVICE_UNAVAILABLE | Предложить повтор; для мутации сначала сверить состояние |

В сохраненном Message.error также возможны GENERATION_TIMEOUT, GENERATION_INTERRUPTED,
LLM_UNAVAILABLE, TOOL_FAILED. TOOL_FAILED завершает ответ только если агент не может
дать полезный ответ после сбоя. Неизвестный код обрабатывается общим сообщением.

## 7. Граница готовности к параллельной работе

### Назначение стажёров (#43)

GET /mentor/available-interns возвращает только свободных intern своей команды,
в порядке name/id. Пустой ответ — {items: []}. Список не резервирует стажёра.
PUT /mentor/interns/{id}/assignment не принимает тело (любое непустое — 422),
mentor_id/team_id берутся из текущей сессии. Новый успех и повтор назначения себе
возвращают 200 с {intern_id, mentor_id, team_id} после commit; чужой наставник в ответе
409 не раскрывается. Несуществующий ID, не intern или другая команда — 404.
Два разных наставника одновременно получают один успех и один 409; два повтора
одного наставника — два 200 и одну запись. Переназначение не поддерживается.

План не требуется и не создаётся назначением: без плана summary имеет 0 шагов/0%,
next_step_id=null, GET плана — 404. UI не отменяет назначение из-за отсутствия плана.
После timeout сначала сверить GET /mentor/interns: наличие стажёра подтверждает
успех. Иначе исход не подтверждён; разрешён явный повтор того же PUT.
После успеха обновить оба списка. Старые вопросы не меняют назначенного владельца;
новые knowledge_gap используют текущее назначение. Повторный seed не отменяет его.

Транзакционный порт mentor.Store.AssignedInternTx(ctx, tx, internID) возвращает
доверенный Principal стажёра, проверяет роли/команду/назначение и удерживает SHARE
до конца переданной tx. Для checkpoint writes брать эти блокировки до plan/step.
Порт не открывает собственную транзакцию и не завершает переданную.

Go реализует транспорт, права и атомарность по этому документу. FE1 реализует диалоги/SSE,
FE2 — план и заявки. Все используют одни примеры и OpenAPI; генераторы не заменяют
тесты поведения. При изменении схемы одновременно обновить примеры, инструкции и проверку.
Здесь не специфицированы внутренние Go-интерфейсы LLM/интеграций — они остаются отдельной задачей.

## Контекст обращения (#57)

Существующие draft/create/reroute принимают необязательный `context_snapshot`;
его подтверждённая серверная проекция хранится на том же вопросе. Снимок с выбранным чекпоинтом
требует актуальную ревизию плана. Направление, исходные сообщения, версии документов и права
стажёра/получателя проверяются при записи и чтении. Недоступные метаданные и зависящие от
закрытых источников цитаты не выдаются; `409 CONTEXT_CHANGED` требует исправить выбранный состав.
GET источника не отмечает открытие. UI после показа подтверждает версию через `/opened`;
POST повторяет проверки прав и идемпотентен. Открытия после отправки не меняют снимок.
Подробнее: [поведение и примеры](../docs/features/question-context.md).
