# Контракт фронтенда и Go-бэкенда

Статус: предложение v0.1 для согласования командой; реализация пока отсутствует.

Область MVP: первая задача → инструкции → отсутствие доступа → подтвержденная заявка
→ сохраненный номер и статус → следующий шаг. Наставнический кабинет и редактирование
планов не входят в этот контракт. Содержимое документов и профили синтетические.

- `openapi.yaml`: HTTP-операции и модели.
- `chat-events.md`: порядок событий, восстановление чата, подтверждение действия.

## Общие правила

- Одна внешняя точка входа Go, префикс /api/v1. React и API доступны с одного origin
  (в разработке используется proxy). Cookie сессии передается браузером.
- Для изменяющих запросов сервер проверяет Origin по списку разрешенных адресов;
  POST/PATCH с телом принимают только application/json. Demo-вход проверяет Origin тоже.
- Реальные интеграционные ключи и ключ LLM никогда не передаются в React.
- Идентификаторы объектов — непрозрачные строки. client_message_id — UUID фронтенда.
- Поля из required обязательны. nullable допускает именно null. Необязательное поле может отсутствовать.
- Даты RFC 3339 в UTC; отображение в часовом поясе пользователя делает фронт.
- Данные вне прав пользователя отфильтровываются сервером до передачи модели и клиенту.
- Прогресс и следующий доступный шаг рассчитывает сервер; granted не завершает автоматически
  шаг «Запустить проект»: его выполнение подтверждает стажер.
- Массивы в ограниченном demo без пагинации. Перед расширением объема данных контракт обновляется.
- Корпоративная имитация должна менять pending на granted/rejected воспроизводимым способом,
  например через отдельную demo-команду. Публичный API не дает стажеру право одобрять себе доступ.
- Все изменения общих структур согласуются с потребителями до изменения реализации.

## Ответственность

Frontend 1: conversations, messages, documents, разбор SSE, источники.
Frontend 2: demo/session, me, plan, карточки заявок и confirm, общий каркас.
Go backend 1: HTTP, сессии/права, хранение, передача потока, план.
Go backend 2: агент и знания, корректное формирование событий и черновиков.
Интеграции: создание внешней заявки без дублей, чтение и сохранение статуса.

## Минимальные приемочные проверки

1. Demo-вход → план → новый диалог с step_id → ответ и доступный источник.
2. Черновик виден в чате, но внешняя заявка до confirm отсутствует.
3. Confirm возвращает/позволяет получить external_id; обновление страницы сохраняет карточку.
4. Повтор confirm не создает второй заявки. Устаревший draft_version дает 409.
5. Обрыв SSE восстанавливается из истории без автоматического повторного действия.
6. Чужие диалоги/документы/заявки недоступны, недопустимые операции запрещены.
7. Ошибка сервиса не отображается как успех. pending и granted различаются.
8. Изменение статуса интеграции обновляет заявку и следующий шаг.

OpenAPI не заменяет SDD: спецификации поведения агента и инструментов оформляются отдельно.
