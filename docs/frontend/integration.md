# Договоренности на стыках фронтенда

## 1. Маршруты и создание диалога

| URL | Владелец экрана | Поведение |
|---|---|---|
| `/login` | FE2 | Только тестовый вход в demo-среде |
| `/onboarding` | FE2 | План и связанные заявки |
| `/chat` | FE1 | Пустой экран нового диалога |
| `/chat?stepId=...` | FE1 | Новый диалог с контекстом шага |
| `/chat/:conversationId` | FE1 | Сохраненный диалог |
| `/` | FE2 | Redirect на `/onboarding` после проверки сессии |

На защищенных маршрутах FE2 сначала загружает me. При 401 — login;
при 503/сетевом сбое — ошибка и повтор, а не ложный выход из аккаунта.
Demo-выбор пользователя не показывается как корпоративная регистрация.

FE2 передает stepId через URLSearchParams. FE1 получает title/description из кеша плана
либо GET plan. Неизвестный stepId показывает ошибку контекста, не создает диалог молча.
При входе подставить «Помоги выполнить шаг: <название>» в поле ввода, без автоотправки.

POST conversations вызывается FE1 только по первой явной отправке пользователя, не из эффекта
монтирования. Передается `{client_conversation_id, step_id}`; без контекста step_id опускается. Пока создание идет, повторная отправка блокируется.
При успехе заменить URL на `/chat/:id`, обновить список диалогов и отправить сообщение.
Контроллер первой отправки должен пережить эту замену URL: запрос не должен отменяться
из-за смены ключа компонента. При неизвестном исходе создания автоматического POST retry нет:
предложить повтор с тем же client_conversation_id и параметрами: сервер возвращает тот же диалог.
ID и неотправленный текст сохраняются в sessionStorage на время создания, привязаны к user.id,
удаляются после успеха/отмены/выхода. После reload требуется явное продолжение пользователем.

Прямой URL восстанавливается через GET /conversations/{conversation_id} и listMessages. Если диалог не найден, показать недоступность и ссылку на новый чат.

## 2. Типы и HTTP-клиент

FE1 создает `shared/api/types.ts` с алиасами из generated/schema.ts:

```ts
import type { components } from './generated/schema';
export type AccessRequest = components['schemas']['AccessRequest'];
export type Message = components['schemas']['Message'];
export type Plan = components['schemas']['Plan'];
// Аналогично User, Step, Conversation, Source, ApiError.
```

При реализации команда генерации (из frontend/):

```sh
npx openapi-typescript ../contracts/openapi.yaml -o src/shared/api/generated/schema.ts
```

Закрепить генератор в devDependencies; не загружать случайную новую версию при каждом запуске.
Сгенерированный файл коммитится вместе с контрактом; CI проверяет, что генерация не дает diff.
OpenAPI nullable означает `null`, optional означает возможность отсутствия поля.
Не заменять это пустыми строками и не использовать any/as для сокрытия несовместимости.

FE1 предоставляет транспорт с результатом `{status, data}`: 202 нельзя терять.
Базовый адрес `/api/v1`; credentials=`same-origin`; JSON тела кодируются централизованно.
204 не разбирается как JSON. JSON-ошибки, не-JSON ответы прокси и network error нормализуются
в единый ClientError с kind, message, опциональными status/code/traceId/fieldErrors.
AbortSignal поддерживается. Автоматические повторы мутаций выключены.
FE2 пишет endpoint-функции своих модулей поверх этого транспорта; FE1 — своих.

Внешний JSON сначала unknown, затем проверяется схемой. Каждая feature владеет runtime-схемами
своих ответов; источником структуры остается OpenAPI. FE2 экспортирует схему AccessRequest
через public API, FE1 использует ее внутри action.proposed. Тестовые ответы проверяются этими же схемами.
При нарушении формата показать ошибку протокола, не отображать непроверенный успех.

## 3. Ключи кеша и обновление

FE1 фиксирует в shared/api/keys.ts общий набор фабрик:

```ts
export const queryKeys = {
  me: () => ['session', 'me'] as const,
  plan: () => ['onboarding', 'plan'] as const,
  conversations: () => ['chat', 'conversations'] as const,
  conversation: (id: string) => ['chat', 'conversation', id] as const,
  messages: (id: string) => ['chat', 'messages', id] as const,
  document: (id: string) => ['documents', id] as const,
  requests: () => ['access-requests', 'list'] as const,
  request: (id: string) => ['access-requests', 'detail', id] as const,
};
```

Один QueryClient на приложение. При выходе, смене пользователя или 401 отменяются активные
запросы/поток, очищаются кеш и локальный текст чата. После очистки переход на login.
Кеши не сохраняются между пользователями в localStorage. FE2 владеет этой очисткой;
FE1 предоставляет остановку своих активных потоков через AbortSignal/размонтирование.

| Событие | Кто обновляет данные |
|---|---|
| PATCH шага | FE2 записывает возвращенный Plan в plan |
| Создание диалога | FE1 обновляет conversations |
| Финал/ошибка чата | FE1 обновляет messages, conversations и инвалидирует plan/requests |
| action.proposed | FE1 передает данные общему механизму приема заявки FE2, добавляет request_id к сообщению |
| Confirm | FE2 записывает заявку, инвалидирует requests и plan |
| Изменение статуса при polling | FE2 обновляет заявку, инвалидирует requests и plan |

Инвалидация означает пометить кеш устаревшим и перезапросить используемые данные.
Фронт не пересчитывает прогресс сам. Пока идет поток, фоновые GET messages не должны затирать
локальный собираемый ответ: FE1 держит stream-state отдельно и объединяет его по message_id.

## 4. Карточка заявки: единственная общая реализация

FE2 публикует из features/access-requests/index.ts:

```tsx
type AccessRequestPanelProps = {
  requestId: string;
  onDiscuss?: () => void;
};
// AccessRequestPanel: контейнер с загрузкой, мутацией и состояниями.
// accessRequestSchema: runtime-схема для событий и HTTP.
// acceptAccessRequest(queryClient, request): обновление кеша из события/HTTP.
```

FE1 вставляет `<AccessRequestPanel requestId={id} onDiscuss={focusComposer} />` для каждого
request_ids сообщения. Контейнер сам использует общий кеш, GET/confirm/polling.
FE1 не реализует свой confirm и не копирует карточку. После перезагрузки те же request_ids
восстанавливают карточки через GET. В плане FE2 использует этот же контейнер.

Внутри FE2 может разделить контейнер и чистый UI:

```ts
type AccessRequestCardProps = {
  request: AccessRequest;
  isConfirming: boolean;
  error?: string;
  onConfirm: (requestId: string, draftVersion: number) => void;
  onDiscuss?: () => void;
};
```

acceptAccessRequest не позволяет устаревшему событию откатить submitting/pending/granted
обратно в draft. Сравнивается revision: меньшая версия игнорируется, равная не заменяет запись, большая принимается.
При противоречии одинаковых revision — ошибка протокола и GET актуального состояния. Дедупликация карточек по request.id. Одна активная мутация confirm на requestId
во всем приложении: отключение кнопки одного экземпляра недостаточно.

## 5. Состояния заявки

| Статус | Текст/действие |
|---|---|
| draft | Показать ресурс, read/write понятными словами, причину; «Подтвердить отправку» |
| submitting | «Отправляем заявку / уточняем результат», повторное подтверждение недоступно |
| pending | «Ожидает согласования», внешний номер; никакого сообщения о выданном доступе |
| granted | «Доступ выдан», номер и обновленный следующий шаг |
| rejected | Причина отказа и «Обсудить с помощником» |
| failed | Причина сбоя, явный повтор confirm по тому же requestId допустим по серверному контракту |

При DRAFT_CHANGED загрузить актуальный черновик и потребовать нового нажатия, не подтверждать
автоматически. После сетевого сбоя confirm сначала GET: исход неизвестен. Если все еще draft,
дать явный повтор с тем же ID. 202 означает продолжить проверку, не объявлять успех.
При failed/rejected без failure_reason показывать нейтральное описание, не придумывать причину.

Polling для submitting/pending — каждые 5 с, пока карточка видима и вкладка активна.
Использовать общий query, не создавать независимые setInterval в каждой копии карточки.
На granted/rejected/failed polling остановить. При возвращении на вкладку обновить состояние.
status_checked_at показывать как время последней успешной проверки; при ошибке сохранять
последний известный статус с отметкой «Не удалось обновить», не менять его на failed локально.

## 6. Источники и поток

FE1 реализует DocumentDrawer с props `{documentId: string | null; onClose: () => void}`.
Использует Drawer FE2. null означает закрытую панель. Данные загружаются через GET document.
Имена/фрагменты источников берутся из Message.sources, номер заявки — из AccessRequest.external_id.
Markdown не исполняет raw HTML, ссылки допускают безопасные URL-схемы.

Полный протокол находится в ../../contracts/chat-events.md. FE1 реализует reader + reducer:
reader разбирает поток, reducer последовательно обновляет состояние по событиям.
Неизвестное event-name можно пропустить для совместимости; известное событие с неверной
структурой означает ошибку протокола и восстановление из GET messages.
EOF без terminal event не является успешным окончанием. Один chunk может содержать несколько
событий или половину символа UTF-8. Статусы инструментов показываются без внутренних рассуждений LLM.

## 7. Что нельзя менять односторонне

- Маршруты, имена экспортов AccessRequestPanel и shared API, ключи кеша.
- Момент создания диалога и семантику stepId.
- Формат событий и правила повторов/подтверждений.
- Версии зависимостей и глобальные стили второго разработчика.

Если API недостаточен, записать конкретный недостающий запрос/поле и согласовать с бэкендом.

## Контекст обращения — #57

`QuestionComposer` расширяет существующие обращения наставнику/HR редактируемым снимком,
необязательным чекпоинтом, выбранными цитатами/инструкциями и ручными попытками. Перед отправкой
стажёр отдельно одобряет точный состав; смена направления требует новой проверки.
`DocumentDrawer` дополнительно принимает `sourceMessageId` для чтения процитированного документа
и подтверждения его показа, либо `contextQuestion: {id,direction}` для разрешённой проекции
источника обращения. Старые props остаются совместимы. Отказ доступа очищает и родительский контекст.
Полный контракт, границы, проверки и запуск: [контекст вопроса](../features/question-context.md).
