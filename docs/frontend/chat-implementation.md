# FE1: диалоги и SSE (#3)

Ветка codex/fe1-chat-sse создана от dev (5fea9b6). В dev на старте были
каркас #1 и транспорт #2; features/session, onboarding и access-requests пока
не публиковали реализацию. Чужие task-ветки не объединялись автоматически.

ChatPage экспортируется из features/chat/index.ts и подключена в app/router.tsx
на /chat и /chat/:conversationId. Новый диалог создаётся только первой явной
отправкой. stepId проверяется по GET plan; неизвестный шаг блокирует отправку.
История и метаданные восстанавливаются независимо от списка диалогов.

API использует один транспорт и QueryClient. Временные boundary-схемы user/plan
находятся в chat/schemas.ts, поскольку публичных схем FE2 в dev ещё нет.
При подключении #4 заменить их импортами FE2, сохранив queryKeys.me/plan.
Новые зависимости и вторые providers не добавлялись.

Контроллер принадлежит странице, переживает внутреннюю replace-навигацию после
создания и отменяется при выходе/смене диалога. UUID создания и исходный вопрос
сохраняются в sessionStorage с user.id, восстанавливаются без автоотправки.
Неопределённый исход сообщения сверяется с историей перед явным повтором UUID.
Одна генерация на диалог; Enter отправляет, Shift+Enter и IME не отправляют.

SSE: streaming TextDecoder, LF/CRLF, много событий в chunk, многострочные data,
heartbeat и неизвестные имена. Известные события проходят runtime-проверку;
reducer проверяет message ID, порядок started и связь финала с вопросом.
Финальный Message заменяет delta. Обрыв/ошибка вызывает GET истории, затем
polling раз в 2 секунды до 130 секунд. POST автоматически не повторяется.
Частичный текст остаётся при восстановлении. Ручное обновление истории доступно.

Оформление использует существующие токены и Button/Spinner/InlineError FE2,
адаптируется к узким экранам. Автопрокрутка действует только у конца истории;
иначе появляется «Новые сообщения». aria-live озвучивает статусы, не каждый токен.
Поиск ui-ux-pro-max по streaming/loading в React не дал проверенного совпадения;
применены контракт проекта и базовые правила доступности, без новой палитры.

MSW содержит детерминированный POST messages, сохраняющий историю до SSE-финала,
и конфликт повторного UUID. Это тестовая имитация, не проверка LLM.
Для браузерного mock-режима FE2 должен передать session/plan handlers через
createHandlers; по умолчанию фиктивная авторизация не добавляется.
Для Go необходима действительная demo-сессия. В текущем dev login/plan остаются
placeholder-экранами; полноценный пользовательский путь требует #4/#5/#7.

Источники, Markdown и AccessRequestPanel внутри сообщений — #6. Сохранённые
sources/request_ids и action.proposed валидируются и сохраняются в состоянии,
чтобы будущая интеграция не зависела от повторного получения SSE.
В #6 action.proposed необходимо передать в acceptAccessRequest FE2 (revision),
а карточки восстановить по request_ids. Confirm в FE1 не реализуется.
Старый ChatPlaceholderPage оставлен как компонент демонстрационного каркаса,
но рабочие маршруты его больше не используют.

Проверки из frontend/: npm ci, npm run typecheck, npm run lint,
npm run test:coverage, npm run build, npm run check:api.
Unit/component-тесты покрывают байтовые разрывы, EOF, ошибки протокола, 409/401,
восстановление, лимит ожидания, создание без дублей, stepId и смену URL.
Проверка с реальным Go/LLM и визуальная проверка в браузере пока не заявляются.

## Интеграция после обновления dev, 2026-11-10

В ветку FE1 объединена dev на 5a6f86d. Конфликт router.tsx разрешён совместно:
LoginPage и PlanPage FE2, RequireAuth вокруг AppShell и ChatPage FE1 на обоих
маршрутах чата. Описанные выше ограничения о заглушках FE2 относятся к исходной
базе ветки и больше не описывают актуальный роутер.

Пять регрессионных тестов в app/router.integration.test.tsx проверяют переход из
настоящего плана в чат, восстановление сохранённого диалога и RequireAuth для
плана и обоих маршрутов чата. Существующие тесты FE1/FE2 сохранены.

В браузере без MSW пройден путь: LoginPage → вход intern_demo_1 → PlanPage →
«Спросить помощника» → проверенный stepId в composer → отправка → SSE от Go →
сохранённый ответ. Обновление страницы и прямой переход на URL диалога
восстановили вопрос, ответ и контекст шага из PostgreSQL.
Использовался серверный demo.Agent: внешний LLM этой проверкой не подтверждён.
Docker Compose: PostgreSQL, миграции, seed и API; frontend на 127.0.0.1:5175,
origin добавлен только переменной окружения процесса Compose, без правки файлов.
