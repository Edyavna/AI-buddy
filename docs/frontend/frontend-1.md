# FE1 — чат, источники и клиентский транспорт

Сначала прочитать README.md и integration.md этой папки. Владение файлами указано там.

## Результат работы

Стажер открывает новый или существующий диалог, отправляет вопрос, видит работу помощника,
получает ответ со ссылками, открывает документ и видит карточку заявки FE2 внутри сообщения.
После обновления страницы история и заявки восстанавливаются.

## Порядок реализации

### Шаг 1. Передать основу второму разработчику

- shared/api: генерация типов, транспорт, ClientError, queryKeys.
- Разделить обычный JSON-вызов и streaming fetch, сохранить HTTP status.
- Тестовый setup и сборка MSW handlers. FE2 подключает свои handlers через отдельный экспорт.
- Зафиксировать публичные функции в index.ts и дать FE2 пример GET и мутации.
- Не ждать готовности настоящего сервера: общий транспорт проверяется на MSW.

### Шаг 2. Диалоги без генерации

- ChatPage и список диалогов; пустой, loading, error и populated состояния.
- Прямой URL диалога, восстановление истории и привязанного шага.
- Переход с stepId, подстановка редактируемого текста без отправки.
- Первая отправка создает диалог по действию пользователя с client_conversation_id; повтор после сетевого сбоя использует тот же ID.
- Enter отправляет, Shift+Enter дает новую строку; учитывать IME composition.
- Пустой/пробельный текст не отправлять; максимум 8000 символов по API.

### Шаг 3. Поток и восстановление

- UUID для одной отправки; сохранение исходного ID для неизвестного сетевого исхода.
- message.started связывает оптимистичное сообщение с серверным ID.
- Отдельно состояния sending, streaming, recovering, failed и idle.
- Во время генерации не запускать вторую в том же диалоге.
- Финальное Message заменяет накопленный текст, а не дописывается повторно.
- При EOF/ошибке сверять историю; при generating опрашивать раз в 2 с по контракту.
- Остановить поток при уходе на другой диалог/выходе. Не отменять его при внутренней
  замене URL сразу после создания того же диалога.
- Не вводить независимый агрессивный timeout короче серверного лимита 120 с.

### Шаг 4. Источники и интеграция карточки

- Markdown, блоки кода, копирование, источники и DocumentDrawer.
- action.proposed передать через acceptAccessRequest, связать ID с текущим сообщением.
- Использовать AccessRequestPanel FE2; временная заглушка только локальная до его поставки.
- Сохраненная история отображает request_ids без зависимости от наличия старого SSE-события.
- Автопрокрутка только если пользователь был у конца. Если читает выше — показать
  «Новые сообщения», не перетягивать страницу вниз.

## Тесты твоей зоны

- Reader: разрыв UTF-8, несколько событий в chunk, разрыв JSON между chunk,
  CRLF/LF, heartbeat, EOF без финала, неверное известное событие.
- Повтор ID, 409 MESSAGE_ALREADY_EXISTS/GENERATION_IN_PROGRESS, 401 и ошибка прокси.
- Финальное сообщение не дублирует delta; частичный ответ сохраняется на экране при сбое.
- Создание диалога не повторяется при ререндере и смене URL.
- Источник загружается, 404 корректно показан, HTML не исполняется.
- Карточка по request_ids восстанавливается после reload.
