# #27: поставка 1 — mock-основа кабинета

Ветка feature/mentor-workspace-foundation создана от dev c9f7f20.
Пользователь подтвердил, что mentor API ещё не согласован: поставка mock-only.
contracts/openapi.yaml, generated types, Message/SSE, outcome агента и backend
не меняются. Модели features/mentor/models.ts изолированы и описывают только
проект из docs/features/mentor-workspace.md. После согласования заменить их
привязкой к generated types в отдельном изменении с backend-владельцами.

Добавлены маршруты /mentor/questions, questions/:id, documents, interns,
interns/:id и перенаправление после входа по роли. RequireAuth сохранён;
MentorGate не заменяет серверную проверку прав. Маршруты стажёра сохранены.
После успешной смены аккаунта старые запросы отменяются, кеш и sessionStorage
очищаются перед установкой новой сессии. Выход использует существующую очистку.
В этой поставке страницы содержат только каркас; действия очереди/загрузки
добавляются поставкой 2, прогресс — поставкой 3.

Из frontend/ в PowerShell:

```powershell
npm ci
$env:VITE_MENTOR_MOCKING = 'enabled'
npm run dev
```

Открыть http://localhost:5173/login и выбрать «Тестовый наставник».
Флаг действует только в dev и явно включает MSW; обычная сборка не подменяет
сбой Go фиктивным успехом. VITE_API_MOCKING остаётся совместимым старым режимом.
Mentor-моки хранят собственные синтетические сессию, вопросы, документы и планы.
История теряется при полной перезагрузке browser mock; реальная сохранность
требует backend. Для тестов createMentorMock(scenario) возвращает handlers и
control. Сценарии: normal, empty, failed, processing, question_changed,
lost_upload. Нет случайных таймеров: processing продвигается чтением,
processing-сценарий остаётся неизменным. Только назначенный intern_demo_1 имеет
план, чужие ID возвращают 404; роль intern — 403, нет сессии — 401.

Проверки: check:api, typecheck, lint, test:coverage, build. Нужна отдельная
реальная интеграционная приёмка после реализации API. Полную готовность #27
эта mock-поставка не объявляет. Три PR предназначены для последовательного
ревью: основа → очередь/знания → прогресс. Последующие ветки включают предыдущую
поставку до её объединения в dev; не объединять в обратном порядке.
