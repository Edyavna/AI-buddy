# Инструкция для двух фронтендеров

Это рабочие договоренности v0.2 для реализации React + TypeScript. Они описывают
будущее приложение: исходники фронтенда и npm-команды пока не созданы.
Локальные технические решения ниже приняты для старта, а не являются требованиями Авито.
Менять их можно согласованно по процедуре в конце документа.

## Как начать

1. Оба читают этот файл, [стыки модулей](./integration.md) и
   [HTTP-контракт](../../contracts/openapi.yaml).
2. Каждый читает свое задание: [FE1 — чат](./frontend-1.md),
   [FE2 — адаптация и заявки](./frontend-2.md).
3. На короткой совместной встрече подтвердить владельцев файлов, экспортируемые интерфейсы,
   тестовые данные и способ запуска. Записать согласованные отклонения здесь.
4. FE2 создает общий каркас, FE1 — API-основу. После соединения минимального каркаса
   оба работают параллельно. Создавать два отдельных React-проекта не нужно.
5. Проверки перед объединением перечислены в [приемке](./acceptance.md).

## Что строим

Стажер открывает план, выбирает шаг, задает вопрос помощнику, читает источники,
подтверждает заявку на доступ и видит сохраненный номер, статус и следующий шаг.
Отдельные кабинеты наставника, редактор планов, регистрация, админка документов,
ручное одобрение доступа стажером и создание заявки обычной формой вне чата — вне MVP.

Источники истины:

| Вопрос | Документ |
|---|---|
| URL, поля, nullable, статусы, HTTP-ошибки | `contracts/openapi.yaml` |
| Порядок событий, обрыв чата, подтверждение | `contracts/chat-events.md` |
| Переходы, идемпотентность, версии и коды ошибок | `contracts/behavior.md` |
| Владение кодом, компоненты, кеш, переходы | Документы этой папки |

При противоречии с API сначала согласовать изменение контракта с Go-разработчиком.
Нельзя молча додумывать отсутствующий эндпоинт или поле.

## Общая техническая основа

- React + TypeScript, strict=true. Один проект `frontend/` на Vite.
- React Router для маршрутов. TanStack Query для серверных данных.
- Локальное состояние React для форм, панелей и текущего потока. Zustand в MVP не нужен:
  не дублируем в глобальном хранилище пользователя, план и заявки из Query.
- `fetch` через общий API-клиент. Для потока отдельный reader поверх fetch, не EventSource.
- Типы OpenAPI генерируются openapi-typescript, не переписываются вручную.
- Zod для проверки входящих HTTP-ответов и событий на границе приложения.
  Тип TypeScript сам по себе JSON по сети не проверяет.
- CSS Modules для локальных стилей, общие CSS-переменные для оформления.
- Vitest + React Testing Library для поведения компонентов; MSW для имитации HTTP;
  Playwright для общего пользовательского сценария.
- Один npm lockfile. FE2 фиксирует совместимые версии при создании проекта и документирует
  используемую версию Node. Дополнительные библиотеки согласуются с владельцем package.json.

## Владение файлами

Это план путей, которые предстоит создать:

```text
frontend/
  src/
    app/                       # FE2: router, providers, AppShell
    shared/
      api/                     # FE1: fetch, ошибки, типы, keys.ts
        generated/             # только генератор
      ui/                      # FE2: общие элементы
      styles/                  # FE2: токены и базовые стили
    features/
      chat/                    # FE1: диалоги, сообщения, SSE
      documents/               # FE1: просмотр источника
      session/                 # FE2: тестовый вход, me, выход
      onboarding/              # FE2: план и изменение шага
      access-requests/          # FE2: загрузка, карточка, confirm, polling
    mocks/
      fixtures/                # FE1: chat/documents; FE2: остальные
      handlers/                # такое же разделение
      browser.ts               # FE1: сборка MSW-обработчиков
    test/                      # FE1: setup, общие helpers
  e2e/                         # FE1: чат; FE2: заявка/план; общий сценарий вместе
```

FE2 владеет package.json, lockfile, tsconfig, Vite-конфигурацией и entrypoint.
FE1 владеет конфигурацией тестов, генерацией типов и схемами протокола потока.
Добавление test-скриптов в package.json делает FE2 по согласованному перечню FE1.
Тесты модуля лежат рядом с его кодом и принадлежат автору модуля.

Разрешенные зависимости: app → features → shared. shared не импортирует features.
Chat может импортировать только публичные экспорты access-requests и documents.
Onboarding открывает chat через URL; не импортирует внутренние файлы чата.
Feature публикует необходимые компоненты/хуки через свой `index.ts`.

## Общий интерфейс

FE2 создает Button, TextField, TextArea, Spinner, InlineError, EmptyState,
StatusBadge, Dialog и Drawer. Пока они готовятся, FE1 использует простые HTML-элементы
или временные локальные обертки, но не добавляет второй набор в shared/ui.
Приоритет — ранняя передача Button, InlineError и Drawer в общий каркас.

Базовые договоренности: русский текст интерфейса, системный шрифт, шкала отступов
4/8/12/16/24/32 px, радиусы 8/12 px. Цвета задаются переменными surface, text,
muted, border, primary, success, warning, danger. FE2 выбирает значения с читаемым контрастом.
Статусы обозначаются текстом, а не одним цветом. FE1 не вводит параллельные глобальные стили.

На ширине менее 768 px навигация сворачивается, источник открывается полноэкранной панелью,
карточки не создают горизонтальную прокрутку. Проверить 360, 768 и 1440 px.
Формы имеют label; кнопки доступны клавиатурой; модальные панели удерживают фокус
и возвращают его на открывшую кнопку. Поток не должен озвучивать каждый токен через aria-live.

## Как изменять договоренности

1. Автор описывает проблему, затронутый интерфейс и потребителей.
2. Для HTTP — согласует с Go; для общего компонента — с его владельцем и потребителем.
3. В одном изменении обновляет документ, типы, моки и затронутые тесты.
4. Сообщает второму разработчику, какой экспорт/поле изменился и как мигрировать.

Каждый работает в своей ветке/рабочей копии. Небольшие законченные изменения интегрируются
регулярно; не ждать готовности всех экранов. При передаче задачи агенту дать этот файл,
свой task-файл, integration.md и HTTP-контракт; ограничить запись своей зоной.
