# Интеграция, тестовые данные и приемка

## Контрольные точки

| Этап | FE1 | FE2 | Совместная проверка |
|---|---|---|---|
| A: основа | API, типы, test setup | Каркас, router, QueryClient, стили | Один проект запускается, me/plan загружаются через MSW |
| B: стыки | ChatPage с контекстом, messages | План, AccessRequestPanel | Из плана открывается чат, карточка FE2 работает внутри него |
| C: сценарий | Поток и источники | Confirm и обновление статусов | Весь путь работает на имитации |
| D: Go | Реальные чат/документы | Реальные session/plan/requests | Те же экраны работают без mock-переключений в feature-коде |
| E: сдача | Тесты своей зоны | Тесты своей зоны | Отчет покрытия, e2e и демонстрация |

Контрольная точка B обязательна до полной полировки интерфейса. Нельзя переносить
первое соединение карточки и чата на последний день.

## Общие fixtures

Fixture — синтетический пример данных для разработки и тестов. FE2 владеет профилем,
планом и заявкой; FE1 — диалогом, сообщениями и документом. Договоренные ID:

| Объект | ID/связь |
|---|---|
| Стажер | intern_demo_1 |
| Команда | team_demo_backend |
| План | plan_demo_1 |
| Шаг | step_local_setup |
| Диалог | conversation_demo_1, step_id=step_local_setup |
| Документ | doc_local_setup |
| Заявка | request_demo_1, связана с шагом и диалогом |
| Ресурс | repo_demo_backend, permission=read |
| Внешний номер | ACCESS-1001 после создания |

Имена сущностей и поля берутся из OpenAPI. Примеры не должны выдавать себя за реальные
регламенты Авито. Один базовый набор, варианты строятся из него без копирования независимых JSON.
Даты фиксированы для воспроизводимости. Для client_message_id используются валидные UUID.
Ассистентские сообщения содержат client_message_id=null, sources и request_ids даже если пусты.

Исходный согласованный набор: [scenario.json](../../contracts/examples/scenario.json).
Его проверяет `scripts/check_contracts.py`. Моки строятся на этих примерах, включая
client_conversation_id, in_reply_to_message_id, revision и allowed_statuses.
Обязательно проверить повтор создания диалога с тем же UUID и прием ответов не по порядку revision.

## MSW-сценарии

- Обычный путь: draft → submitting → pending → granted.
- Отказ сервиса: pending → rejected.
- Достоверный сбой создания: failed, внешний номер отсутствует.
- Устаревший черновик: confirm 409 DRAFT_CHANGED, GET возвращает увеличенную версию.
- Неизвестный сетевой исход confirm: запрос оборван, последующий GET возвращает pending.
- Обрыв потока: история возвращает interrupted с частичным текстом.
- Нет подходящих знаний: ответ честно сообщает об отсутствии информации, sources пуст.
- Ошибка/задержка сервиса, 401, чужой объект 404.

Имитация хранит состояние между запросами внутри теста, поэтому confirm меняет последующий GET.
В тестах reload состояние обеспечивает серверный mock/e2e backend, а не потерявшийся JS-массив браузера.
Mock-режим явно включается только для разработки/тестов, в обычной сборке нет скрытого fallback
на успешный ответ при сбое Go. Переходы статуса в тестах управляемы, не зависят от случайных таймеров.

## Сквозной тест (FE1 и FE2 вместе)

1. Войти тестовым стажером, получить план.
2. Нажать «Спросить помощника» у шага. Проверить контекст, отсутствие автоотправки.
3. Отправить вопрос, увидеть статус инструмента, части ответа и источник.
4. Открыть источник и вернуться в чат без потери сообщения.
5. Получить черновик. Убедиться через тестовый сервис, что внешней заявки еще нет.
6. Подтвердить. Проверить ровно одно создание и показ external_id.
7. Перезагрузить страницу: номер и статус сохранились, повторной отправки нет.
8. Перевести имитацию в granted. Дождаться обновления карточки и плана.
9. Отметить выполненный шаг, получить новый прогресс с сервера.

Дополнительно пройти отказ, устаревший черновик и обрыв SSE.
Сквозные проверки имитации не доказывают работу DeepSeek: полный сценарий с реальным Go/LLM
проверяется отдельно и явно отмечается в отчете о готовности.

## Проверки перед объединением

FE2 создает scripts совместно с FE1. После появления проекта обязательны:

```sh
npm ci
npm run generate:api
npm run typecheck
npm run lint
npm run test:coverage
npm run build
npm run test:e2e
```

Пока package.json отсутствует, это требуемые будущие scripts, а не уже работающие команды.
Повторная generate:api не должна менять актуальные закоммиченные типы.
Unit/component-тесты проверяют поведение, а не количество вызовов внутренних функций.
Coverage считает весь прикладной src, включая еще не импортированные тестами файлы;
исключаются только generated, тесты и тестовые mocks/fixtures. Компоненты и обработчики не исключать.
Порог lines установить 81%, чтобы явно выполнить требование ТЗ «больше 80%».
Сохранять воспроизводимые text/HTML/LCOV-отчеты; итоговый охват проекта согласовать с бэкендом.

## Definition of Done — что означает «готово»

- Реализованы нормальный путь, загрузка, пустое состояние и ошибки своей функции.
- HTTP и события соответствуют контракту; нет any для обхода ошибок типов.
- Нет собственного второго API-клиента, кеша заявки или набора общих кнопок.
- Проверены 360/768/1440 px, клавиатура, отсутствие скачков прокрутки.
- Соседний разработчик подключил публичный экспорт без чтения внутреннего кода.
- Тесты и сборка проходят, покрытие измерено; невыполненные live-проверки перечислены.
- Документы и примеры обновлены, если изменился контракт.

Сдавать работу с краткой записью: что реализовано, какие экспорты доступны, какие команды
проверки прошли, какие ограничения остались. «Работает у меня на моках» не равно интеграционной готовности.
