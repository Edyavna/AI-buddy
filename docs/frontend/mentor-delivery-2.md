# #27: поставка 2 — вопросы и знания (mock-only)

Основана на feature/mentor-workspace-foundation. Объединять в dev после поставки 1.
OpenAPI и generated types не меняются: mentor API пока не согласован.

Очередь фильтруется по статусу, карточка открывается по прямому URL. Доступны
контекст, стажёр, шаг, дата, связанные документы, взятие в работу, повторное
открытие и явное решение. Решение требует непустой комментарий и готовые
документы; mock-сервер повторяет эти проверки. 409 обновляет вопрос и документы,
показывает конфликт и требует повторного действия без автоматического PATCH.

Загрузка: название, один непустой UTF-8 .md до предложенного лимита 1 MiB.
Используется общий API-клиент с FormData; браузер выставляет multipart boundary.
upload_id и неизменяемые параметры сохраняются на экране до подтверждения ответа.
После сетевого/5xx/неожиданного ответа кнопка повторяет тот же запрос, поля
заблокированы. Уход с экрана отменяет запрос; после ухода незавершённая локальная
попытка не сохраняется — следует сначала проверить список документов.
Документ проходит processing → ready/failed, для failed есть явный retry.
Загрузка не решает вопрос. Опрос активных экранов — 5 секунд, без опроса скрытой
вкладки, запросы отменяются при уходе. Неизвестный ответ не показывается успехом.

Просмотр использует существующие Drawer/MarkdownContent, Escape и замыкание Tab.
401/403/404 скрывают кешированные заголовки, персональные данные и содержимое;
временные ошибки отображаются с повтором. История mock хранится только в памяти.

Запуск из frontend в PowerShell:

```powershell
$env:VITE_MENTOR_MOCKING = 'enabled'
npm run dev
```

Открыть /login, выбрать «Тестовый наставник», открыть вопрос, перейти «Добавить
документ», загрузить .md, дождаться готовности, вернуться к вопросу, выбрать
готовый документ и написать комментарий. Подтвердить решение вручную.
Моки не связывают это с outcome/SSE/уведомлениями: они принадлежат другим задачам.

Проверки Vitest/RTL/MSW включают фильтр, прямую ссылку, решение/повторное открытие,
конфликт revision, processing/failed/retry, валидацию файлов, потерянный ответ и
одинаковый upload_id, серверную идемпотентность multipart, отзыв доступа после
успешной загрузки для 401/403/404, клавиатуру Drawer. Multipart проверяется в Node
с настоящими File/FormData; UI-проверка повтора использует имитацию API, поскольку
jsdom File несовместим с native Undici multipart. Новые зависимости не нужны.
Проходят 196 тестов, строки 95,34%; typecheck, lint, check:api и production build.
Реальный Go/LLM и визуальная приёмка 360/768/1440 остаются отдельной проверкой.
