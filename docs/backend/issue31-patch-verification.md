# Issue #31: автоматическая приёмка PATCH решений

Основа: `dev` после PR #40 (`2a76a26`). Добавлен
`backend/internal/app/knowledge_gaps_patch_test.go`; публичный контракт и рабочая
логика не изменяются. Тесты используют настоящие PostgreSQL/pgvector, миграции,
HTTP handlers, загрузку документов, worker индексации и `knowledge.Uploads.CheckReady`.
Только embeddings подменены детерминированным провайдером, платные API не нужны.

## Гарантии

- Два PATCH с одной revision и разными комментариями/документами сначала
  одновременно ожидают блокировку строки в PostgreSQL. После освобождения ровно
  один получает 200, второй — 409 QUESTION_CHANGED. В БД остаётся полное решение
  победителя, revision увеличивается один раз, история содержит одну запись.
- Повтор с текущей revision и теми же полями не меняет persisted state, updated_at,
  resolved_at или историю. Повтор с устаревшей revision даёт 409, после чего клиент
  должен сверить GET. Это существующий контракт, а не новая трактовка повторов.
- Reopen сохраняет комментарий/документы и snapshot предыдущего решения. Новый
  handler и GET стажёра читают то же состояние из БД.
- processing/failed, другой автор, другая команда и отсутствие доступа у одного
  участника не допускают решение. В списке сначала идёт доступный документ, затем
  запрещённый: отклонённый PATCH не оставляет частичных изменений.
- Anonymous, стажёр, другой наставник и наставник после удаления назначения не
  могут изменить вопрос. Сравнивается вся строка вопроса и вся история.
- Отзыв ACL параллельно сохранению ожидает настоящую SQL-блокировку CheckReady
  до commit. После отзыва новое изменение решения с этим документом отклоняется.

Ожидание конкуренции проверяется через `pg_stat_activity` в изолированной тестовой
БД; произвольных sleep нет, ожидания ограничены timeout.

## Запуск

12 ноября 2026 локально прошли целевые PostgreSQL-тесты, весь backend-набор
`go test ./...` и `go vet ./...` (Go 1.27.0/Windows). Целевые тесты также прошли
с `-race` в Linux-контейнере Go 1.26.5 на PostgreSQL 17/pgvector 0.8.7.
Удалённый CI для этих новых файлов ещё не запускался.

Из корня проекта поднять только тестовую БД отдельным Compose-проектом:

```powershell
docker compose -p ai-buddy-issue31 --profile test up -d --wait db-test
```

Из `backend`:

```powershell
$env:TEST_DATABASE_URL='postgres://buddy:buddy_test_only@localhost:5433/buddy_test?sslmode=disable'
go test -v -count=1 -timeout=2m ./internal/app -run TestPostgresKnowledgeGap
go test -count=1 -timeout=3m ./...
go vet ./...
```

Без TEST_DATABASE_URL PostgreSQL-тесты локально пропускаются; такой запуск не
является приёмкой. Testkit создаёт отдельную БД на каждый тест и удаляет её после.
Существующий backend CI уже выполняет эти тесты через `go test -race ./...` с
PostgreSQL, дополнительная настройка workflow не нужна.

Для race требуется CGO/C-компилятор. На Windows без него используется одноразовый
Linux-контейнер `golang:1.26.5`, та же версия Go, что в CI, с исходниками read-only
и TEST_DATABASE_URL на `db-test:5432` в сети `ai-buddy-issue31_default`.

Ручная браузерная приёмка, живые LLM/embeddings и измерение качества ответов сюда
не входят и остаются отложенными по решению владельца проекта.
