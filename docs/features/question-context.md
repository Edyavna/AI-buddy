# Контекст обращения наставнику или HR — #57

Ветка `feature/question-context-preview`, база `dev` — `740c3da` (включает #62, #56 и #58).
Используется существующее обращение `knowledge_gaps`, его ID, очередь, назначение наставника,
история, группировка и публикация инструкций. Второй сущности эскалации нет. Назначения issue не меняются.
Миграция `000019_question_context.sql` добавляет nullable JSON-снимок в обращение и черновик,
а также минимальную таблицу подтверждённых открытий. Старые данные не переписываются.

## Пользовательский путь

1. Стажёр открывает обычный чат или «Спросить помощника» из плана. После ответа выбирает
   «Обратиться к специалисту». Существующая подсказка классификатора #62 остаётся видимой;
   направление можно изменить вручную, в том числе после уточнения или для двух частей вопроса.
2. Сервер предлагает цитатный черновик из **сохранённого реального диалога**: до 12 последних
   подходящих сообщений, по 800 Unicode-символов, и до 10 доступных источников.
   Рабочие и кадровые ответы фильтруются по направлению; сообщения уточнения допускаются в обоих.
   Это извлечение цитат, без пересказа моделью и без автоматически выдуманных попыток.
3. Стажёр редактирует вопрос и ручное резюме, выбирает/редактирует отдельные цитаты,
   необязательный чекпоинт и источники, вводит собственное описание попыток.
   Цитаты сохраняют ID исходного сообщения; редактирование явно обозначается специалисту.
   Ничего необязательного не отмечено заранее. Непереданные фрагменты в снимок не попадают.
4. Предложенный источник отличается от открытого. Получение GET само по себе ничего
   не отмечает: после показа разрешённого текста панель подтверждает его версию отдельным POST.
   Отмена загрузки/закрытие до показа не считаются открытием. Ошибка подтверждения не создаёт
   ложную отметку. Это сигнал отображения в UI, **не доказательство внимательного чтения**.
5. Перед отправкой виден точный выбранный состав, требуется отдельное подтверждение вопроса,
   адресата и всего контекста. Любая правка снимает подтверждение. Смена направления очищает
   несохранённый контекст; для нового направления проверяются новые доступные фрагменты.
   Если ранее явно сохранён черновик этого направления, восстанавливается именно он.
6. Сначала сохраняется черновик, затем отправляется обращение. Неудачная доставка оставляет
   сохранённый черновик доступным после reload. Сохранённый вручную адресат имеет приоритет
   над предложением модели. Несохранённые изменения при недоступности самой записи остаются
   в открытой форме; офлайн-автосохранение в браузер не добавлено.
7. Наставник/HR видит выбранные цитаты, ручное резюме, попытки «со слов стажёра», чекпоинт,
   источники и отметку открытия **на момент отправки**. Последующее открытие не меняет снимок.
   Специалисту доступны только явно переданные фрагменты и разрешённые документы, не весь чат.
   Автор может перейти к исходному сообщению по прямой ссылке с выделенным местом прокрутки.

Развёрнутая форма использует ширину сообщения и обычную прокрутку страницы. Сохранены
компоненты, токены и стиль Авито; кликабельные элементы контекста имеют высоту не менее 44 px.

## Контракт и проверки доступа

Пути ниже относительно `/api/v1`; пример запроса/снимка —
[question-context.json](../../contracts/examples/question-context.json), схемы —
[OpenAPI](../../contracts/openapi.yaml), generated TypeScript обновлён генератором.

| Метод и путь | Назначение |
| --- | --- |
| `GET /messages/{id}/question-context?direction=mentor\|hr` | Доступный цитатный черновик, чекпоинт с ревизией плана, источники с текущими версиями |
| `GET /messages/{id}/context-documents/{document_id}` | Чтение действительно предложенного в этом диалоге документа |
| `POST /messages/{id}/context-documents/{document_id}/opened` | Идемпотентное подтверждение показа `{ "version": 1 }` после повторной проверки прав |
| `PUT /messages/{id}/question-drafts/{direction}` | Существующее сохранение черновика с необязательным `context_snapshot` |
| `POST /messages/{id}/questions` | Существующая отправка с `operation_id` и подтверждённым снимком |
| `POST /questions/{id}/reroute` | Смена адресата того же обращения с `revision`, `operation_id` и новым снимком |
| `GET /questions/{id}/context-documents/{document_id}` | Чтение выбранного источника автором обращения |
| `GET /{mentor\|hr}/questions/{id}/context-documents/{document_id}` | Чтение выбранного источника разрешённым специалистом |

`QuestionContextInput`: `reviewed`, `include_step`, nullable `step_revision`, `attempts`,
массивы `{message_id,text}` и `{document_id,version}`. Клиент не назначает роли, заголовки,
доступность, флаг открытия или ID чужого чекпоинта. Сервер формирует эти поля самостоятельно.
`context_excerpt` остаётся ручным резюме. Снимок добавлен в общие `RoutedQuestion` и `KnowledgeGap`.
Для старых клиентов поле необязательно; существующий API без снимка сохраняет совместимость.

На запись проверяются владелец диалога, команда, порядок сообщений до выбранного ответа,
направление, принадлежность чекпоинта и текущая ревизия плана, реально предложенные документы,
версии и доступ стажёра **и получателя**. Назначение наставника/область HR проверяются сервером.
Сохранение черновика, отправка, перечитывание контекста и смена направления используют
порядок блокировок `команда → связанные строки`; send не удерживает сообщение в ожидании команды.
Изменение чекпоинта, версии или недоступная ссылка дают `409 CONTEXT_CHANGED`; сбой БД — 503.

На каждом чтении снимок заново проверяется. Закрытый источник возвращается с `title: null`
и `status: unavailable`. Цитата ответа, опиравшегося на закрытый/изменившийся источник, также
скрывается; старый текст не извлекается из `Message.sources`. Исторические JSON-снимки API
не возвращают `context_snapshot`; исходный аудит в БД сохраняется. Черновики очищают недоступные
цитаты и требуют исключить отсутствующие ссылки перед новой отправкой.

Отказ 401/403/404 очищает тело и заголовок документа, а также родительские копии предпросмотра/
снимка. Старое поколение запросов отменяется; поздний 200 и последующая 503 не возвращают
закрытые данные. Logout/смена аккаунта используют общий session scope и очистку кеша.
Ручной текст автора не классифицируется сервером как содержимое источника и остаётся ручным текстом.

Повторные отправки используют прежний механизм идемпотентности #62: один ID обращения,
ключ операции и хеш **включая весь одобренный снимок**. При потерянном ответе клиент сверяет
вопрос, направление, резюме и точный выбранный контекст с сервером. Смена payload с тем же ключом
даёт конфликт. Двойной клик блокируется до окончания операции.

Группировка #58 и генерация инструкций #56 продолжают ссылаться на тот же вопрос. Они используют
собственные явные проекции вопроса/решения; приватный снимок целиком в общую инструкцию не передаётся.

## Воспроизводимая проверка

Для чистой среды нужны Docker/Compose, Node из `frontend/.node-version`, Go 1.26.5.
Команды запускаются из корня репозитория в bash; для PowerShell задайте переменные через `$env:`.
Не используйте `down -v` для рабочей БД.

```bash
npm --prefix frontend ci
export COMPOSE_FILE=compose.yaml:scripts/compose.hr-test.yaml
docker compose up --build --wait --wait-timeout 180 frontend hr-fixture
docker compose --profile demo run --rm seed
npm install --no-save --package-lock=false playwright-core@1.60.0
npx playwright-core install --with-deps chromium
node scripts/question-context-browser.mjs
docker compose restart api hr-fixture
docker compose up -d --wait api hr-fixture
docker compose --profile demo run --rm seed
node scripts/question-context-browser.mjs --verify
```

Сайт — `http://localhost:5173`; демо-вход «Тестовый стажер», «Тестовый наставник», «Анна, HR».
Сценарий проходит обычные маршруты и SSE с настоящими Go/PostgreSQL, загрузку/публикацию
документов, открытие/возврат фокуса/Escape, удаление цитаты, редактирование, явное подтверждение,
сохранение/reload, карточку специалиста, запрет чужого чата, 360/768/1440 px и restart/reseed.
Отчёт и снимки создаются в `tmp/question-context-browser/`; `--verify` использует сохранённый отчёт.
Для своего Chromium доступны `CONTEXT_BROWSER` и `CONTEXT_PLAYWRIGHT_MODULE`.

Детерминированный HTTP-провайдер заменяет только внешнюю модель. Для N57 он действительно
запрашивает поиск и чтение разрешённого документа через инструменты агента. Генерация черновика
контекста не использует LLM вообще. Живая внешняя модель в этой поставке не проверялась.

Проверки доступа до/после отправки, реальный отзыв HR-документа, удаление документа, смена
наставника/его персонального доступа, версии, чужие объекты/команды, отсутствие HR, пустая история,
ошибки хранилища, отмена запросов, конкуренция и повторные операции проверяются API-тестами
с отдельными PostgreSQL-базами. Component-тесты дополнительно проверяют смешанный вопрос,
уточнение, ручной режим при ошибке, смену направления, точное одобрение, потерянный ответ,
logout и закрытый кеш после последовательности 200 → 401/403/404 → 503.
