# Подготовка Markdown-инструкции

Режим подготовки инструкции использует общий чат наставника. «Знания команды» →
«Сгенерировать Markdown» открывает `/mentor/chat?mode=markdown` без автоматической
отправки и создания документа. Первый вопрос создаёт диалог с `markdown: true`;
прямой URL `/mentor/chat/:id` восстанавливает этот режим из сохранённого диалога.

Запустите проект по корневому README. Для подключённой модели настройте LLM из
`.env.example`. В явном demo-режиме без модели возвращается демонстрационная инструкция.

## Пользовательская проверка

1. Войдите как наставник и откройте «Знания команды» → «Сгенерировать Markdown».
2. Опишите инструкцию. Если помощник запросит рабочие факты, отправьте уточнение в тот же диалог.
3. Скачайте первую версию через «Скачать .md». Попросите помощника внести правку и скачайте вторую версию.
4. Перезагрузите страницу. Убедитесь, что ссылки в истории скачивают соответствующие версии в UTF-8.
5. Откройте ссылку на диалог во второй сессии наставника. Чтение и отправка сообщения должны вернуть 404.
6. В «Знаниях команды» укажите название и выберите скачанный файл. Нажмите «Загрузить документ», чтобы начать индексацию.
7. В тестовой среде подставьте управляемый ответ модели с ошибкой. После ошибки нажмите «Повторить запрос» и проверьте, что предыдущие версии доступны.

## Версии и ограничения доступа

Подключённая модель вызывается без инструментов стажёра. Она получает собственную
историю диалога, задаёт уточнения при недостатке рабочих фактов и возвращает полную
версию после правок. Завершённый ответ с outcome `answered` получает отдельную ссылку
«Скачать .md». Файл `instruction.md` содержит точный текст выбранного ответа в UTF-8;
уточнение, generating/failed/interrupted не считаются готовыми версиями.

Сбой сохраняется в истории. Явный повтор использует исходный вопрос и новый UUID
сообщения. Предыдущие версии остаются доступными. Общие лимиты истории сохраняются:
до 19 прошлых сообщений и 24000 символов с текущим вопросом, только полные успешные пары.
Публикация выполняется существующей multipart-формой исключительно после нажатия
«Загрузить документ». Генерация и скачивание не вызывают загрузку/индексацию.

Сервер проверяет владельца, команду и роль наставника для чтения, истории, отправки,
списка и архива. После потери роли автор не видит Markdown-диалоги даже в собственном
архиве. Другой пользователь получает 404; HR не имеет доступа к API чата (403).
Смена обычного нового чата на Markdown-режим отменяет предыдущее поколение запросов,
сохраняя возможность явного продолжения отдельного черновика после неизвестного
исхода создания. Внутренняя замена URL после успешного создания не отменяет SSE.

## Интеграция с dev

PR #78 переведён с ветки #77 на `dev e7ef2ff`. Объединены архив, Markdown-флаг,
проверки доступа, кеши и исправление повтора загрузки списка из #77. Конфликтовавшая
миграция перенесена на `000027_mentor_markdown.sql`, после уже выпущенной `000026`.
Отдельный PostgreSQL-тест применяет миграции поверх dev с архивным диалогом и повторно
проверяет Apply/Verify: архив сохраняется, старые чаты остаются обычными.

При ревью исправлена отправка устаревшего запроса при переключении режима во время
создания диалога. Регрессионный тест сначала воспроизвёл заблокированную отправку,
затем проверил, что поздний ответ старого создания не отправляет вопрос и новая
инструкция создаётся с правильным флагом.

## Автоматическая сквозная проверка

Из корня в bash, на отдельном Compose project со свободными стандартными портами:

```bash
export COMPOSE_FILE=compose.yaml:scripts/compose.hr-test.yaml
docker compose -p mentor-markdown-75 up --build --wait --wait-timeout 180 frontend hr-fixture
docker compose -p mentor-markdown-75 --profile demo run --rm seed
npm install --no-save --package-lock=false playwright-core@1.60.0
npx playwright-core install --with-deps chromium
node scripts/mentor-chat-browser.mjs
node scripts/mentor-markdown-browser.mjs

docker compose -p mentor-markdown-75 restart api hr-fixture
docker compose -p mentor-markdown-75 up -d --wait api hr-fixture
docker compose -p mentor-markdown-75 --profile demo run --rm seed
node scripts/mentor-chat-browser.mjs --verify
node scripts/mentor-markdown-browser.mjs --verify
```

В PowerShell задавайте `$env:COMPOSE_FILE` с платформенным разделителем `;`.
Можно переопределить `MENTOR_APP_URL`, `MENTOR_BROWSER`, `MENTOR_PLAYWRIGHT_MODULE`.
HTTP-фикстура принимает фактическую историю из Go, проверяет наличие предыдущей
полной версии, возвращает уточнение, версии и управляемый однократный сбой.

Сценарии используют настоящий Go, PostgreSQL, cookie-сессии, SSE, браузерные загрузки
файлов и существующую multipart-форму. Проверяются 360/768/1440 px, побайтовое содержимое
каждой версии после reload, архив/возврат с клавиатуры, сохранение версий при сбое и
повторе, изоляция второго наставника и стажёра, отсутствие автоматической публикации,
загрузка выбранной второй версии и её успешная индексация. После restart/reseed
проверяются сохранённые версии и загруженный текст. Общий сценарий #77 проверяет
обычный чат наставника и чат стажёра с его контекстом и формами.

CI выполняет эти шаги через production Nginx SPA; артефакт `mentor-markdown-browser`
содержит скриншоты, скачанные `.md` и синтетические ID. Локально использованы Chrome,
Vite, Go и PostgreSQL. Внешняя модель с настоящим ключом не проверялась.

## Команды проверок и покрытие

В `frontend/`: `npm run typecheck`, `npm run lint`, `npm run check:api`,
`npm run test:coverage`, `npm run test:e2e`, `npm run build`.
Локально для покрытия использован `--maxWorkers=2`.

В `backend/`, с `TEST_DATABASE_URL` на тестовую PostgreSQL с pgvector и правом CREATEDB:

```bash
go test -race -count=1 -timeout=2m -coverpkg=./... -coverprofile=coverage.out ./...
go vet ./...
go build ./...
go run ../scripts/go_line_coverage.go coverage.out
mkdir -p coverage
go run ../scripts/go_line_coverage.go --lines coverage.out > coverage/lines.tsv
node ../scripts/hr-coverage.mjs origin/dev backend
```

В `frontend/` для изменённых строк: `node ../scripts/hr-coverage.mjs origin/dev frontend`.
Локальный Linux-прогон на Docker Desktop применяет `-p 1 -timeout=5m`; исходный CI-лимит
2m и пороги не увеличены. Обе проверки изменённых исполняемых строк строго >90% включены
в CI для этой ветки. Контракты: `python scripts/check_contracts.py` после установки
`contracts/requirements-check.txt`.
