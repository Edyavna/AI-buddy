## Пользовательский путь

1. Наставник или ответственный HR решает вопрос в своём кабинете.
2. «Подготовить инструкцию» открывает `/mentor/questions/:id/instruction` или
   `/hr/questions/:id/instruction`. Источник содержит направление, исходный вопрос,
   проверенный ответ, команду, ревизию и связанный чекпоинт.
3. Автор пишет текст вручную или явно запрашивает предложение помощника. Ошибка модели
   не удаляет ручной текст. Генерация ограничена пятью секундами, ничего не публикует
   и повторно проверяет доступ после ответа модели.
4. Можно создать документ либо дополнить доступный для редактирования опубликованный
   документ. Показаны существующий текст, версия, добавляемый Markdown и полный список
   команд-аудиторий. Для наставника доступны собственные общекомандные документы;
   для HR — готовые версии с покрытой областью редактирования и командой стажёра.
5. «Сохранить черновик» записывает его отдельно в PostgreSQL. Reload восстанавливает
   сохранённый текст; несохранённые правки обозначены явно. При конфликте черновика
   перечитайте его версию кнопкой сверки. При конфликте документа обновите исходный
   документ и снова сохраните дополнение. Ручной текст и название при обновлении
   исходного документа сохраняются; автоматического повторного опубликования нет.
6. Публикация доступна после сохранения и явной отметки о проверке текста и аудитории.
   Состояния: `draft` → клиентское «Публикуем…» → `indexing` → `ready` либо `failed`.
   Неизвестный исход записи/публикации сверяется отдельным GET; при недоступной сверке
   редактор предлагает явную проверку, не сообщает неподтверждённый успех.
7. Существующий worker индексирует материал. Только после успешной индексации ссылка
   добавляется к вопросу в той же транзакции. Стажёр видит её в обращении внутри чата.
   Следующий ответ агента использует доступную опубликованную версию и её источник.
   Сбой индексации имеет явный повтор с теми же документом и версией.

Готовая публикация из одного решения неизменяема через этот редактор: новое дополнение
оформляется из другого решённого вопроса. При обновлении уже опубликованного документа
предыдущая версия остаётся в поиске до готовности новой. История версий сохраняется.

## API и согласованность

Для обеих ролей общий суффикс `/{mentor|hr}/questions/{id}/instruction-draft`:

| Метод и суффикс | Результат |
| --- | --- |
| `GET` | Актуальный источник, собственный черновик или `null`, до 100 последних доступных целей |
| `PUT` | Сохранение с `revision` (0 для первого сохранения) и проверкой `base_version` |
| `GET /targets/{id}` | Текущий текст, версия и аудитория выбранного документа |
| `POST /generate` | Предложение `{title, content, mode}` без сохранения и публикации |
| `POST /publish` | Явная публикация сохранённой ревизии с `reviewed: true` |
| `POST /retry` | Повтор неудавшейся индексации той же публикации |

Пример тела `PUT`:

```json
{"revision":0,"title":"Настройка сервиса","content":"## Настройка\nПроверьте конфигурацию.","target_document_id":null,"base_version":null}
```

Пример публикации: `{"revision":1,"reviewed":true}`. Стажёр, другой ответственный,
чужая команда или отозванный источник/документ не дают права читать или публиковать
черновик. `409 INSTRUCTION_CHANGED` требует перечитать данные и явного нового действия.
`400/422`, `401`, `403`, `404`, `503` используют штатный `ApiError`.
Примеры и nullable-схемы — `contracts/examples/resolution-drafts.json` и OpenAPI;
TypeScript перегенерирован штатной командой.

Публикация блокирует строку черновика и проверяет ревизии источника и цели. Документ,
версия и задание индексации сохраняются вместе. Повтор после потери ответа возвращает
ту же публикацию, включая одновременные запросы. Сбои записи откатывают всю транзакцию.
Worker повторяет проверку источника и прав перед публикацией индекса; потерявший claim
worker не фиксирует ни индекс, ни ссылку. Связь вопрос → документ/версия хранится
в `resolution_drafts`, а событие готовности — в истории вопроса.

Черновики не включаются в `knowledge_documents` и поиск. В модель не передаются ID
стажёра, переписка или cookie. Из входа и предложения удаляются распознаваемые ключи,
пароли, PEM-ключи, JWT, email и телефоны. Публикация текста с обнаруженными секретами
отклоняется. Это не автоматическое доказательство обезличивания: автор обязательно
просматривает материал и удаляет персональные обстоятельства перед публикацией.
Markdown использует существующий безопасный рендерер без HTML и загрузки внешних картинок.

## Проверка из чистой среды

Используйте отдельный Compose-проект/том для теста. HTTP fixture не требует реальных
ключей. Следующие команды из корня одинаково задают оба Compose-файла без зависимости
от разделителя путей ОС:

```sh
docker compose -p buddy-issue56 -f compose.yaml -f scripts/compose.hr-test.yaml up --build --wait frontend hr-fixture
docker compose -p buddy-issue56 -f compose.yaml -f scripts/compose.hr-test.yaml --profile demo run --rm seed
npm install --prefix tmp/resolution-browser-tools --no-save --package-lock=false playwright-core@1.60.0
```

Откройте `http://localhost:5173/login`. Для автоматической проверки задайте
`RESOLUTION_APP_URL=http://localhost:5173`, `RESOLUTION_PLAYWRIGHT_MODULE` — абсолютный
путь к `tmp/resolution-browser-tools/node_modules/playwright-core/index.mjs`.
Установите Chromium командой `npx --prefix tmp/resolution-browser-tools playwright-core install chromium`
или задайте `RESOLUTION_BROWSER` существующим браузером. Затем:

```sh
node scripts/resolution-drafts-browser.mjs
docker compose -p buddy-issue56 -f compose.yaml -f scripts/compose.hr-test.yaml restart api hr-fixture
docker compose -p buddy-issue56 -f compose.yaml -f scripts/compose.hr-test.yaml up -d --wait api hr-fixture
docker compose -p buddy-issue56 -f compose.yaml -f scripts/compose.hr-test.yaml --profile demo run --rm seed
node scripts/resolution-drafts-browser.mjs --verify
```

Сценарий создаёт синтетические вопросы и документы. Отчёт и снимки сохраняются в
`tmp/resolution-browser`. Для строгой проверки выбранной версии используйте чистый
тестовый том: fixture embeddings намеренно одинаковые, поэтому чужие старые тестовые
инструкции могут попасть в выдачу при повторе на загрязнённой базе.
Браузерный job закреплён на Ubuntu 24.04, поддерживаемой Playwright 1.60.0;
обновление `ubuntu-latest` до 26.04 не должно ломать установку браузера.
В CI тот же сценарий проверяет **production SPA через Nginx** и настоящий Go в Compose,
включая перезапуск и повторный seed.
