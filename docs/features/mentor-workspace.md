# Кабинет наставника и пополнение базы знаний

Статус: согласованное направление продукта, проект API для реализации.
Frontend-владелец новой функции — Никита. Основная ветка — dev.
Первая серверная поставка добавляет назначенных стажёров и планы в OpenAPI.
Очередь вопросов и документы остаются проектом API для следующих поставок.

## Пользовательский результат

Стажёр задаёт вопрос, на который нет подтверждённого ответа в доступных документах.
Он передаёт вопрос наставнику. Наставник видит вопрос, добавляет Markdown-документ,
дожидается успешной индексации и отмечает вопрос решённым. Стажёр получает
уведомление в приложении и может повторить вопрос. Ответ содержит источник.
Наставник также видит прогресс назначенных ему стажёров.

Первая версия использует существующую роль mentor. Отдельная роль руководителя,
редактор планов, Slack/email и автоматическое одобрение доступа в объём не входят.
Чекпоинт — существующий шаг плана; формулу прогресса сохраняем.

## Определение отсутствия ответа

Агент возвращает один из результатов: answered, needs_clarification, knowledge_gap.
knowledge_gap означает, что поиск успешно завершён, но подтверждённого ответа нет.
Отказ LLM, embedding или БД является технической ошибкой и не создаёт пробел знаний.
Для needs_clarification агент задаёт уточняющий вопрос.
При knowledge_gap стажёр нажимает «Передать наставнику». До нажатия запись очереди
не создаётся. Сервер назначает наставника и команду по доверенным данным.
Повтор для одного исходного сообщения возвращает прежнюю запись.
Способ передачи outcome в Message/SSE необходимо согласовать с владельцами чата
и обновить контракт. Поиск слов «не знаю» в тексте ответа не применяется.

## Кабинет наставника

После входа mentor открывается /mentor/questions. Основные разделы:
- /mentor/questions — очередь и фильтр new/in_progress/resolved.
- /mentor/questions/:id — вопрос, стажёр, шаг, безопасный контекст сообщения,
  связанные документы и действия «Взять в работу», «Добавить документ», «Решить».
- /mentor/documents — знания команды, загрузка .md и состояния индексации.
- /mentor/interns — назначенные стажёры, прогресс, следующий шаг, блокировки.
- /mentor/interns/:id — план выбранного стажёра только для чтения.

Используем текущие токены, AppShell, Drawer, Button и общий QueryClient.
Роутинг по роли должен сохранять вход и рабочие маршруты стажёра.
При выходе/смене аккаунта очищаются кеш и активные запросы.
403/404 не должны оставлять старые персональные данные или документы на экране.
Ошибки 503/сети отображаются с повтором, без фиктивного успеха.

## Документы и решение вопроса

Минимальная загрузка: название и один UTF-8 .md файл, до 1 MiB.
Предел — предложенное продуктовое значение, согласовать с backend перед реализацией.
Команда и автор назначаются сервером. Произвольный HTML не исполняется.
Документ имеет состояние processing, ready или failed. В поиск попадает только ready.
Ошибка индексации видима, доступен повтор для failed.
Два нажатия/сетевой повтор загрузки с одним upload_id не создают два документа.
Идемпотентность действует для одного автора и одинакового содержимого.
Тот же ключ с другим содержимым возвращает 409.

Для resolved нужен хотя бы один доступный ready-документ и непустой комментарий
наставника. Решение явно подтверждается наставником и проверяется сервером.
Загрузка сама по себе вопрос не закрывает. Повторное открытие вопроса разрешено.
Стажёр видит решение и ссылку, повторный LLM-запрос запускает явно.
Опрос активных экранов раз в 5 секунд, остановка при скрытой вкладке/уходе.
Никаких внешних уведомлений для MVP.

## Проект HTTP-контракта

Префикс /api/v1, текущая cookie-сессия и ApiError, даты UTC RFC3339.
Все mentor-операции требуют mentor и проверяют назначение/команду на сервере.
Права на документы фильтруются до передачи содержимого модели или клиенту.

| Операция | Результат |
|---|---|
| GET /mentor/questions?status=... | {items: KnowledgeGap[]} |
| GET /mentor/questions/{id} | KnowledgeGap |
| PATCH /mentor/questions/{id} | {status, revision, resolution?, document_ids?} → KnowledgeGap |
| GET /mentor/documents | {items: MentorDocument[]} |
| POST /mentor/documents | multipart: upload_id UUID, title, file, question_id? → 202 MentorDocument; повтор → существующий объект |
| GET /mentor/documents/{id} | MentorDocument с безопасным content для просмотра |
| POST /mentor/documents/{id}/retry | 202 MentorDocument, только failed; повтор processing идемпотентен |
| GET /mentor/interns | {items: InternSummary[]} |
| GET /mentor/interns/{id}/plan | существующий Plan |
| POST /messages/{id}/knowledge-gap | создать по подтверждению стажёра, первый 201, повтор 200 |

KnowledgeGap: id, student{id,name}, step_id|null, message_id, question,
context_excerpt, status(new/in_progress/resolved), revision, document_ids[],
resolution|null, created_at, updated_at. Полную чужую переписку не возвращать.
MentorDocument: id, title, status(processing/ready/failed), author{id,name},
created_at, updated_at, error|null; detail дополнительно content.
InternSummary: id,name,team{id,name},progress_percent,next_step_id|null,
completed_steps,total_steps,blocked_steps,open_questions (null до подключения очереди).
404 для чужого объекта; 401 без сессии; 403 для неверной роли; 422 для валидации;
409 QUESTION_CHANGED при устаревшей revision, 409 DOCUMENT_NOT_READY при попытке
решить вопрос с неготовым документом. После 409 обновить данные и потребовать
повторного осознанного действия. Семантические проверки выполняет сервер.

Это предложение для обсуждения frontend/backend, не действующий контракт.
Первый PR Никиты должен добавить согласованный OpenAPI и сгенерированные типы.
До согласования допускаются изолированные mock fixtures, без изменения текущих
Message/SSE и без объявления интеграции с backend готовой.

## Приёмка

- Наставник видит только назначенных стажёров и разрешённые материалы.
- Передача вопроса и повтор не создают дубли.
- Технический сбой не записывается как knowledge_gap.
- Загрузка проходит processing → ready либо failed; повтор работает.
- До ready решить вопрос нельзя; конфликт версии не маскируется успехом.
- Уход со страницы/перезагрузка восстанавливают серверное состояние.
- Видимы loading/empty/error; клавиатура, фокус, ширины 360/768/1440 проверены.
- OpenAPI/types, typecheck, lint, component tests, coverage и build проходят.
- Отдельно проверен путь со стажёром, настоящими Go и LLM после интеграции.
- Измеряются время до решения, число повторных вопросов с ответом и доля ошибочных
  эскалаций; это предлагаемые метрики, значения собираются в пользовательском прогоне.
